# MVP в режиме «ресёрч-проект» (а не продукт)

Постановка (Кирилл, 2026-05-29): реализуем не как коммерческий продукт, а как
**исследовательский проект с доступом к информации**. Что тогда нужно в MVP.

## Вердикт по реформулировке

**Умный де-риск, рекомендую.** Снимает два самых тяжёлых риска из
[[analogs-and-lessons]] / [[need-and-demand]]: готовность платить и
cold-start/дезинтермедиацию маркетплейса. Совпадает с [[approach|build-first и
«прибыль не на старте»]]. И это **самый юридически защищённый формат** из всех
обсуждённых — аналитика о рынке, а не потребительская витрина.

Две честные оговорки:
1. **Нет forcing function.** Без выручки и пользователей-клиентов проект живёт
   только на околонулевой стоимости + твоей мотивации. Риск — «красивый ресёрч,
   которым никто не пользуется». Лечится тем, что у инфы должен быть хотя бы один
   реальный читатель/потребитель (ты сам как байер, пара знакомых заведений, TG).
2. **Ядро инженерии не меньше.** Сбор+нормализация данных нужны в любом режиме;
   экономим только на продуктовой обвязке (аккаунты, оплата, UX), а не на пайплайне.

## Юридическая рамка (не юрсовет)

«Ресёрч» — не волшебный щит. Реклама по ФЗ-38 = информация для *неопределённого
круга* с целью *продвижения*. Из этого:
- **Защищённая зона:** аналитика и агрегаты о рынке, тренды стилей, списки
  пивоварен как юрлиц, обезличенные сигналы спроса. Это не продвижение продукта.
- **Рискованная зона:** публичный потребительский каталог с названиями, ценами,
  «где купить», рейтингами — выглядит как продвижение, как его ни назови.

Вывод: выход держим либо **аналитическим/агрегированным**, либо с **ограниченным
доступом** (не «неопределённый круг»). См. [[risks]].

## Что меняется относительно продуктового [[mvp]]

**Убираем из MVP:** paywall/тест готовности платить, аккаунты и онбординг,
транзакции, полированный потребительский UX, механику маркетплейса.

**Добавляем/усиливаем:** методологию и прозрачность покрытия; слой публикации
(отчёты/датасет).

**Не меняется:** ядро сбора данных — нужно в любом режиме.

## Что нужно в MVP (ресёрч-режим)

1. **Пайплайн сбора** — парсеры TG + магазины ([[parser-architecture]]).
   Бэклог: `task-1`, `task-2`, `task-10`.
2. **Хранилище + дедуп + провенанс research-grade** — у каждого факта источник,
   дата, уверенность ([[data-model]]). Бэклог: `task-3`.
3. **Слой сигнала спроса** — скидки + отзывы во времени = собственно находки
   («что продаётся / что нет», тренды стилей). Это **заголовочный выход** ресёрча.
   Бэклог: `task-9`, `task-10`.
4. **Методология и покрытие** — задокументировано: какие источники, как
   категоризируем, % покрытия по городам/стилям, известные дыры, свежесть данных.
   Без этого ресёрчу не верят.
5. **Слой доступа/публикации** — самое лёгкое, что отдаёт инфу наружу:
   автогенерируемые отчёты/дайджесты (это уже умеет наш [[autonomy|LLM-wiki]]),
   browseable-датасет или открытый CSV/JSON. **Рекомендация:** начать с
   периодических отчётов + queryable-датасета, а не с потребительского веб-аппа.

Не нужно: монетизация, аккаунты, заказы, ЕГАИС.

## Доступ — РЕШЕНО: открытый

Кирилл (2026-05-29): доступ открытый. Значит держим публичный выход
**агрегированным/аналитическим** (справочник + мета + тренды + контент), а
гранулярную B2B-аналитику — под замком/по запросу. Это закрывает юр-рамку и задаёт
форму витрины — см. [[reference-site]] («Dotabuff российского крафта»).

## Дверь в продукт оставляем открытой

Актив — это **данные и петля** ([[mvp]]), а не форма подачи. Если ресёрч покажет
ценность, поверх того же пайплайна включается аналитика-как-продукт
([[monetization]]) без переделки. То есть ресёрч-режим = дешёвая, защищённая
первая ступень, не тупик.
